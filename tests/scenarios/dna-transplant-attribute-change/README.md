## 录制与规则事实

- 双端录制 `8c4fc7dd343f4a909bb611977cab2995`，确定性单局 1v1，双方勾选“不洗牌”；Host 后来投降，Guest 胜。原始清单状态 `validated`，编译报告 `compiled`，Host 10 步、Guest 8 步、无阻断。本目录的两份 YDK 与录制草稿逐字节一致，双方各 40 张主卡组、无额外卡组。
- Host 的表侧「地狱亡灵」（40575313，怪兽区 3）初始属性为暗 `32`；Guest 的表侧「火山鼠」（33112041，怪兽区 2）初始属性为炎 `4`。Host 发动已盖放的「DNA移植手术」（56769674）并宣言神 `64`，两只怪兽均变为神。Guest 再发动自己盖放的同名卡并宣言风 `8`，两只怪兽均变为风。两张陷阱到终局都保持表侧。

## 目标逐项审核

1. **已验证**：两次陷阱发动、两次属性宣言均来自录制中的实际动作。剧本在 Host 宣言前核对暗／炎，第一次宣言后 `wait_for` 核对双方怪兽都为神；Guest 下一次决策仍核对神属性。
2. **已验证**：Guest 宣言后 `wait_for` 核对两只怪兽都为风，双端终局可见快照也均为风，双方陷阱仍在魔陷区表侧。
3. **已验证**：双端 Agent 已接受的事件历史分别断言「Host 陷阱发动 → 两只怪兽暗／炎变神 → Guest 陷阱发动 → 两只怪兽神变风」。事件只报告可见数值、区域和格子，不声称每次属性变化的引擎因果；发动事件和变化事件的先后由场景核对。
4. **未验证的扩展情况**：陷阱表侧期间新怪兽入场、陷阱离场后的属性恢复、效果无效、与其他属性修改效果的覆盖关系；这局没有这些操作。

## 协议缺口与修复

录制时，原生客户端在 `MSG_UPDATE_DATA` 中已显示属性变化，但旧 Agent v3 历史只在决策时取得快照：Host 跳过中间的神属性，Guest 终局服务镜像还停留在上次决策时的神属性。修复后，客户端复用可见卡序列化，比较同格同已知表侧卡的已观察数值，通用地生成 `card_value_changed`；本剧本的 `field` 为 `attribute`。事件经 HTTP v3 决策或同步写入两端 Agent 历史。`/v3/sync` 按契约仅同步事件，不刷新快照；终局后查询服务镜像仍可能看到上次决策的快照，须同时看事件截止点。本场景以两端原生终局可见快照及 Agent 历史断言完整过程。
