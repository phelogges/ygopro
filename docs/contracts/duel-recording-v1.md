# 双客户端人工对局录制契约 v1

> 状态：现行人工双客户端录制及草稿生成契约。录制 JSONL 的 `schema_version: 1` 与场景 YAML、Agent HTTP 版本分别管理；确定性与随机场景输出分别遵循 [场景 v1](agent-scenario-v1.md) 和 [随机扩展 v2](agent-scenario-v2.md)。

本契约定义本地人工 LAN 单局 1v1 对局的录制、离线场景生成及验证。录制文件包含双方隐藏信息，只供本地编译和诊断，不得交给仅代表一名玩家的 Agent。游戏服务端、`ocgcore`、卡片脚本及既有 CTOS/STOC 联网协议保持不变。

## 会话与入口

建议在启动 GUI 前准备 `goal.md`，用 `--goal-file PATH` 原样复制到录制目录，并在清单记录来源。文件由开发 Agent 保存用户原话及单独的目标整理；录制器不解释目标。既有录制可事后补目标，但必须注明目标提出时间。

`tools/record-duel.py` 是标准入口：它为一局生成不可变的 UUID `record_id`，可接受供人辨认的短名称，分别启动 `host`、`guest` 普通 GUI 客户端。人工完成建房、入房、选卡组和决斗。启动器在 `out/duel-recordings/<record_id>/` 保存本次录制，运行中只报告启动、入房与配置、卡组提交、开局、单方及双方终局、编译和回放验证等状态变化；退出时打印记录、剧本和验证结果的绝对路径。提供最近录制的查询入口，显示名称、ID、状态和大小；删除必须显式指定记录 ID，不自动清理。

录制用 `--scenario-kind deterministic|random` 显式声明场景类型，默认 `deterministic`。两类都要求单局 1v1、不洗牌、起手五张、LP 8000、每回合抽一张、无时间限制；`random` 只表示测试目标效果的结果随机，不能控制该结果。“不检查卡组”可开可关，因为它只影响准备阶段的卡组合规检查，不改变决斗中的牌序。双方入房后、决斗开始前检查参数。未启用“不洗牌”立即记配置失败、保存诊断并关闭本次启动的两个 GUI 进程；其他参数不符同样失败，但保留窗口供排查。类型不从结果自动推断，也不在编译失败后降级。未通过配置检查的录制不得进入场景验证。

## 文件与事件

两端分别按实际发生顺序追加 `host.jsonl`、`guest.jsonl`，一行一个 UTF-8 JSON 对象。每条记录含 `kind`、`role`、本端严格递增的 `seq` 和时间戳。时间戳仅供阅读，不能用于推断跨端因果顺序；跨端关系依据同一 `record_id`、收发包及提示和响应的对应关系建立。首条 `session` 含 `schema_version: 1`、共同 `record_id`、角色及 `controller_space: local`。保留对现有 v1 JSONL 的读取能力；不兼容的事件语义变更须升级版本并提供迁移或明确拒绝诊断。

| `kind` | 必要内容 | 用途 |
| --- | --- | --- |
| `wire_packet` | 收发方向、原始帧编码 | 排查缺失或错配，必要时重建提示和响应；不直接成为 YAML 动作 |
| `room_joined` | 单局/双打模式、`no_shuffle_deck` 等房间参数 | 开局前确定性检查 |
| `deck_submitted` | 实际发出的 `main`、`extra`、`side` 卡片 ID 有序列表 | 以开局前最后一次被房间接受的提交生成 YDK |
| `visible_snapshot` | 游戏消息类型、本端可见状态 | 验证起手与步骤前后状态 |
| `prompt` | 本端 `prompt_id`、提示、合法候选、可见状态、原始游戏消息 | 固定某次决策的上下文 |
| `response` | 对应 `prompt_id`、原始响应、反解出的语义动作或错误 | 只把实际提交的响应转为剧本动作 |
| `duel_start`、`duel_end` | 对局边界、权威赢家 | 检查完整性与终局 |
| `surrender` | 发起方和原有投降协议发送事件 | 生成显式投降目标 |
| `connection_closed` | 连接超时、远端关闭或网络循环提前结束的原因 | 尽快将未到终局的录制标为中止 |
| `replay_save_pending`、`replay_save_resolved` | 客户端是否等待人工处理录像保存弹窗 | 单方已终局时暂停短宽限期，处理完成后重新计时 |

响应反解后须用原有动作编码逐字节复核；多个合法动作编码到同一响应时报告歧义。`select_places` 响应的 `controller_space: local` 表示选区玩家编号已转换为本端视角。`prompt_id` 和候选临时 ID 只用于本次录制内配对；生成 YAML 时使用稳定字段。同形候选自动写入录制时的匹配序号与预期匹配数量，报告列出这些步骤；回放匹配数量或后续状态不符时才要求人工审阅，不猜测另一个候选。存在可发动候选的连锁放弃是显式步骤；没有可发动候选的自动放弃只保留诊断，不进入 Agent 决策或场景步骤。

每端默认日志上限为 100 MiB，可通过启动参数调整。临近上限时明确预警；达到上限后标记不可验证并保留已写记录，不能静默截断后宣称成功。原始 JSONL、进程日志、诊断和生成草稿均留在 Git 忽略目录，不自动提交或清理。

## 清单、终局与失败

每次录制维护 `manifest.json`，记录名称、ID、创建时间、客户端及卡库版本或文件哈希、Git 提交与工作区是否有改动、房间参数、当前阶段、失败原因、产物路径和验证结果。不得记录密钥或环境变量内容。清单在启动后即存在，阶段改变时更新；正常或失败结束都写最终状态。下次查询时若发现仍是运行中的状态但进程已不在，显示为异常中断，不得显示为成功。

只有双方各自收到终局消息、都有 `MSG_WIN`，且权威胜者一致，才算完整录制；自然胜负、平局与投降均遵循此条件。单方终局后只等待短暂宽限期；若另一端正等待人工处理录像保存弹窗，宽限期暂停，弹窗处理后重新计时，总录制时限仍生效。逾期时报告两端最后事件。连接中断、窗口提前关闭、主动取消、总超时、缺一端、会话错配及日志截断均保留原始资料并标记 `aborted` 或相应失败状态，不自动生成“已验证”剧本。正常结束及自动验证后默认保留本次录制的两个 GUI，便于查看结算和保存游戏录像；`--close-clients` 使启动器在结束时关闭其创建的窗口。

## 合并、输出与验证

合并器核对两个角色的同一 `record_id`、本端序号、房间设置、已确认卡组、提示与响应配对和双方权威终局。`host.ydk`、`guest.ydk` 保留实际提交顺序；`scenario.yaml` 遵循 [场景契约](agent-scenario-v1.md)，双端 `expect` 只包含对应端当时可见的数据。中文 `timeline.md` 按决策顺序描述双方实际选择、回合阶段、关键公开状态变化和终局，卡片尽可能同时显示中文名与 ID；每个事件附角色与原始 `seq`。跨端无法可靠对齐的事件不靠时间戳猜测顺序。

确定性完整录制默认自动编译，并由 `tools/agent-e2e.py --scenario ...` 运行一次无界面双客户端回放。编译成功仅代表生成草稿；只有回放中的提示、动作、状态和终局一致才标记 `validated`。随机录制完成后生成 `scenario.unverified.yaml`，标记 `review_required`；编译器检查双方恰有一次目标随机操作，但无法推断效果完成边界。开发 Agent 审查录制、将固定动作截到效果完成后的 checkpoint，并补每结果可见状态断言后，才能按 [随机场景扩展](agent-scenario-v2.md)执行。随机结果导致后续玩家动作分叉的剧本当前不能完整回放。未知提示或首次回放偏差须有定位明确的诊断，不能凭一次偶然吻合认定普遍可靠。GUI 播放另行目视验收。通过验证的场景由用户手动选择并放入 `tests/scenarios/`，工具不自动晋升或提交。已有 `.yrp` 的单文件导入不属于 v1。

旧版 JSONL 及编译器的 `--analysis-draft` 可用于历史录制的离线诊断；分析草稿始终是 `draft_unverified`，不得当作新标准入口或固定牌序回归场景。
