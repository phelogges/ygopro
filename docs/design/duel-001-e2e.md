# 复杂决斗场景 `duel-001` 设计

> 状态：历史场景设计。适用于 `duel-001` 初次制作与验证阶段；继任的现行场景以 `tests/scenarios/duel-001/` 文件为准，格式以[场景 v1 契约](../contracts/agent-scenario-v1.md)为准。

## 背景与目标

`duel.md` 给出双方固定起手、两回合卡片展开、效果连锁、Link/同调召唤和 Host 投降。目标是在现有双客户端 LAN 无界面入口中逐步执行并验证该剧本，失败时指出首个偏差。场景文件位于 `tests/scenarios/duel-001/`；双方均使用场景目录内的 YDK 副本。Host 的 `host.ydk` 保留 `deck/test/host1.ydk` 的前五张及原有顺序，另加入一张 `53927851`。

这张额外卡是完整剧本所必需的：达维先从卡组将唯一的派比安加入手牌，而米克拉之后只能从卡组特殊召唤派比安。直接使用原 `host1.ydk` 时，米克拉的合法候选不含该卡，场景会在此处失败。场景专用副本避免覆盖用户维护的原卡组。

Guest 的 `guest.ydk` 固定了录入剧本时已验证的前五张起手 `56651978, 14558127, 24203749, 12375297, 27204311`，并把第六张固定为第二回合抽到的 `13597785`。后来 `deck/test/guest1.ydk` 的前六张顺序发生变化，场景继续引用该共享文件时，Guest 首回合缺少 `12375297` 和 `27204311`；可拒绝的连锁都被默认放弃，直到 Host 步骤 48 才表现为缺少 `53927851` 的反制候选。场景专用副本固定这一真实前置条件，不改共享卡组。

## 边界

仍使用现有服务端和 `ocgcore`；不修改 CTOS/STOC 协议。固定牌序房间保证两个 `#main` 前五张为起手，但不保证所有引擎随机事件可控。罗莎等效果检索后引擎会发送手牌洗切消息，本场景以 `allowed_random_events: [hand_shuffle]` 明确允许；决策始终按卡片 ID 和当前合法候选匹配，不依赖洗切后的手牌顺序。剧本按双方客户端可见信息断言，不能检查对方隐藏手牌或牌库。`duel.md` 的场地区域编号从 1 开始，YAML 的 `sequence` 依客户端协议从 0 开始；主怪兽区 1～5 映射为 0～4，额外怪兽区按实测候选填写。

## 执行结构

1. `Scenario` 按角色维持步骤游标，匹配当前提示、卡片与效果候选，将语义动作交给 `agent_sdk` 和客户端二次校验。每个关键效果的目标、素材、检索结果以及场面变化写为明确步骤或可见断言。
2. 剧本显式启用 `defaults.optional: decline`。只有非脚本且可拒绝的 `chain`、`yes_no`、`effect_yes_no` 可自动选择 `pass`/`decline`；强制效果、无拒绝候选、选卡、选区及主阶段命令仍立即报错。记录每次自动拒绝供报告审计，防止把未出现的关键动作当成通过。
3. 投降由测试器在双方脚本步骤耗尽、最后可见断言成立后创建一次性本地信号文件。仅 Host 的 `LanTestRunner` 测试模式读取该信号并发送现有 `CTOS_SURRENDER`。之后双客户端必须收到一致的 `MSG_WIN` 和 `STOC_DUEL_END`，且赢家为 Guest。
4. `tests/scenarios/` 按场景子目录组织；既有固定起手和基础连锁场景继续作为小范围回归。

## 风险与验证

- 客户端提示可能包含额外的合法选择；按真实候选编写唯一语义选择器，不持久化临时候选 ID。出现卡片效果不可发动、素材不合法、目标不合法时，诊断保留首个失败提示和可见快照，不改动服务端来迁就剧本。
- `defaults.optional` 只处理可拒绝提示；所有被忽略的提示计数和候选要可追溯。关键阶段用 `wait_for` 与下一步前置断言核对，不仅依赖最终胜负。
- macOS CMake 构建、CTest、Python 单测和双客户端真实 LAN `duel-001` 必须通过。既有两个场景重跑；Windows 按既定顺序放到最后。
