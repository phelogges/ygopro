# 人工对局录制与场景生成

> 状态：现行流程设计。录制格式、房间约束、失败语义与验收条件以[录制契约](../contracts/duel-recording-v1.md)为准；操作入口见[人工录制指南](../guides/manual-duel-capture.md)。

## 背景与取舍

手写完整决斗展开容易遗漏合法候选、连锁询问和实际效果处理。录制模式让用户在两个普通 LAN 客户端中手动完成对局，再从双方各自可见的提示、状态和已提交响应生成可执行的场景。游戏服务端、`ocgcore`、卡片脚本及 CTOS/STOC 协议不变。

单个 `.yrp` 包含双方卡组、随机种子和响应，理论上可经引擎重放恢复询问，但不直接保存客户端当时的合法候选及可见状态。因此当前以双客户端语义录制为主要来源；已有录像的单文件导入仍是后续工作。

## 数据流与责任

`tools/record-duel.py` 为 Host、Guest 启动普通 GUI 客户端，分配同一录制身份和两份独立日志。用户完成房间、卡组及决斗操作；客户端录制器独立于 Agent HTTP 服务，分别保存本端可见状态、合法候选和实际发出的响应。离线编译器核对双端记录，反解语义动作，生成场景、双方卡组及带来源定位的时间线。原始双端记录可能包含各自隐藏信息，只供可信的本地编译；生成的单方断言只取该方当时可见的数据。

录制器按每端真实顺序记录数据，跨端关联依靠协议事件和决策配对，不靠墙钟推断先后。编译器在信息不足或前后不一致时保留原始证据，报告首个无法确定的位置，交给开发 Agent 和用户审核。无有效发动候选的自动连锁无需成为脚本决策；有实际选择的放弃应保留，避免丢失决斗时点。同形候选采用录制时可重验的序号方案，具体匹配语义由[场景契约](../contracts/agent-scenario-v1.md)规定。

## 验证与生命周期

录制从建房前开始，到双端确认权威终局或报告中止。录像保存弹窗可能推迟结束消息，因此录制生命周期须识别待处理弹窗，避免把正常决斗过早判成单端终局。房间条件、终局条件、宽限期、日志上限和中止状态的规范定义只在录制契约维护。

编译稿默认再经无界面双客户端回放，结果和原始录制分开保存；GUI 回放用于人工观看。编译或回放失败不应被“已有 YAML”掩盖。场景断言围绕用户测试目标和双端可见证据选择，避免机械复制每帧快照；场景目标与审核流程见[场景制作设计](duel-scenario-authoring.md)。工具不会自动把草稿加入 `tests/scenarios/`，由用户审核后选择收录。历史录制的分析草稿只用于诊断，不宣称可执行回归。

录制产物、操作命令与故障处理集中在[人工录制指南](../guides/manual-duel-capture.md)；已执行验证与限制见[验证总览](../validation/README.md)。
