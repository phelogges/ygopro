# 人工对局录制与场景生成

## 背景与目标

手写完整决斗展开容易遗漏合法候选、连锁询问和实际效果处理。录制模式让用户在两个普通 LAN 客户端中手动完成单局 1v1，再从双方各自可见的提示、状态和已提交响应生成可执行的场景 YAML。游戏服务端、`ocgcore`、卡片脚本及 CTOS/STOC 协议不变。

单个 `.yrp` 包含双方卡组、随机种子和响应，理论上可经引擎重放恢复双方询问；它不直接保存客户端当时的合法候选及可见状态。本期以双客户端语义录制为主；已有录像的单文件导入留待后续。

## 数据流

`tools/record-duel.py` 为 Host、Guest 启动正常 GUI 客户端，并给两端传入共同录制 ID、角色和不同的日志路径。用户照常建房、入房、选择卡组和操作。客户端的录制器独立于 Agent HTTP 服务，在解析决策提示后保存当前合法候选及本端可见状态，并把最终发出的既有 CTOS 响应反解为语义动作。录制器同时保存实际提交的主、额外和副卡组顺序、房间设置、权威终局及诊断帧。

标准入口只启动确定性录制，生成 UUID 作为机器 ID，并可附加人可读名称。两端入房时即检查单局 1v1、不洗牌、起手五张、LP 8000、每回合抽一张和无时间限制；“不检查卡组”不影响牌序，可开可关。未启用“不洗牌”时保存诊断、报配置失败并关闭启动器创建的两个窗口；其余房间参数不符也报失败，但保留窗口。进度仅在状态变化时输出，避免逐条刷原始包。入口提供最近记录查询、大小查看和显式删除；默认不删除旧录制。

离线合并器先验证双端录制 ID、角色、房间参数、最终提交卡组、提示与响应配对、日志完整性及双方终局。每端使用本地递增序号关联决策；跨端只用协议事件校验同一对局，不靠墙钟推断动作先后。原始记录可同时包含双方隐藏牌，仅用于可信的本地编译；生成的每端 `expect` 只用对应客户端当时可见的数据。

合并器输出独立的 YDK、中文双端时间线、来源定位及场景 YAML。玩家在存在可发动候选时选择放弃，是显式场景步骤；没有可发动候选的空连锁窗口仅保留诊断。场景按实际决策精确回归，不推断通用策略。同形候选自动编码为录制时的匹配序号及预期匹配数量，并在编译报告列出；回放时必须仍有相同匹配数且动作、后续状态一致。无法可靠反解或回放不符时，停止并给出角色、序号、原始提示与响应供人工审阅。

每端继续使用单一追加式 JSONL，包含原始收发包及语义事件，保留本端真实记录顺序。时间戳仅用于阅读，跨端顺序依赖协议与决策配对。每端默认限制 100 MiB，接近时预警，达到上限时该录制不可验证。`manifest.json` 从启动时建立，持续记录名称、ID、创建时间、客户端和卡库文件哈希、Git 版本与脏状态、房间参数、阶段、失败原因和产物路径。状态写入须能在失败路径执行；下次查询看到未结束的运行态应提示异常中断，而不是成功。记录中不含密钥和环境变量内容。

## 验证与边界

`STOC_REPLAY` 可能让客户端等待人工处理录像保存弹窗，阻止后续 `STOC_DUEL_END` 的解析。录制器记下弹窗待处理和已处理事件；一方已终局而另一方仍在弹窗时，短宽限期暂停并在弹窗处理后重新计时，总录制超时仍生效。

录制从建房前开始，直到双方收到权威决斗结束。完整终局要求双端都收到结束消息、各自存在 `MSG_WIN` 且胜者一致；自然胜负、平局和投降一视同仁。单端收到终局后给另一端短暂宽限期，逾期报告各端最后事件。断线、主动取消、提前关闭客户端或总超时标为中止，保留原始证据。正常结束后默认保留 GUI 供查看结算，`--close-clients` 用于批量录制。以实际提交且被房间接受的卡组生成 YDK。可观测随机事件须符合场景契约；无法重现时保留草稿和首个差异，不标记为通过。

生成后默认运行一次无界面双客户端回归；通过才称为可执行场景。`--gui` 播放是单独的可选目视验证。断言以提示、回合、阶段和相关可见区域为主，避免逐字复制所有瞬时快照；只有具备可靠动作后顺序时才生成 `wait_for`。中文时间线展示实际选择、回合阶段、关键公开状态和终局，并以角色及原始序号定位；卡片尽可能同时显示中文名与 ID。

日志截断、缺失一端、会话错配、中途断线和不支持的提示均保留诊断并判失败。原始记录和草稿默认在 Git 忽略的 `out/duel-recordings/`；仅由用户手动选定的场景复制到 `tests/scenarios/`，工具不自动晋升。旧版 v1 JSONL 应继续可编译；历史录制的 `--analysis-draft` 仅供离线诊断，不作为新录制模式。Windows 验证按项目既定顺序留到最后。
