# Agent 可见状态、事件与差异处理设计

## 背景与目标

一期客户端已能在决策时发送完整可见快照和候选，但 v1 的事件在 HTTP 提交后即清空，且多数游戏消息只有类型记录。完整快照能说明**现在可见什么**，不能复原这段时间发生的完整经过。二期模型还需要在有限上下文中读取简洁变化，又能按需查看整体场面。

本设计用每次决策的完整权威快照、连续确认的观测事件、确定性差异和服务端只读状态镜像解决这两个问题。协议见 [HTTP v2 契约](../contracts/agent-http-v2.md)。游戏服务端、CTOS/STOC、`ocgcore` 与卡片脚本不改变。

## 组件与数据流

```text
游戏消息 → 客户端原有解析 → 可见性过滤 → 连续事件日志
                                      ↘ 决策时冻结完整快照、候选
                       客户端主动 POST /v2/sync 或 /v2/decision
                                      ↓
                 agent_sdk：验证、事件连续性、状态替换、净差异
                                      ↓
          Agent 服务：持久化、构造模型输入、只读状态查询、调度
                         ↙            ↓             ↘
                 模型历史工具      模型决策       人类只读视图
                                      ↓
         模型输出结构化意图 → agent_sdk 校验/翻译语义动作
                                      ↓
          客户端复核当前提示与版本 → 原有响应编码 → 游戏服务端
```

`agent_sdk` 使用 Python 3.12，实现与 LLM 框架无关的状态模型、严格解析、差异计算、候选／动作校验和只读查询。Agent 服务拥有持久化事务、模型调用和请求调度；模型不能改写权威状态，也不能生成游戏协议字节。客户端保留完整本方可见快照的权威来源；服务端每次接受更高版本时替换镜像，而不对客户端发送增量命令。模型工具与人类视图读取同一份已确认状态，不各自维护场面副本。

## 客户端采集与可见性

客户端在游戏消息处理完成、状态与候选一致后冻结一次决策包。一次包中的 `state_version`、快照、事件截止点及 `prompt_id` 指向同一时点；冻结后收到的消息排入下次。只在真实需要选择时请求 Agent；没有有效选择的自动连锁不产生模型请求。终局事件通过同步接口发送。人工接管期间继续记录本方可见事实。

`ClientField` / `ClientCard` 是 GUI 缓存，不是可直接导出的语义模型。每个纳入快照的字段要写清：源消息或查询、玩家可见条件、值的有效期、未知表示、对应验证案例。当前首版白名单在 HTTP 契约中，包含禁用区域、墓地查看权限、连锁深度、已确认的动态属性及正面卡的素材／装备／指定对象关系；UI 描述提示等仍待进一步纳入。每个区域的 `hidden_count` 必须等于 `count - cards.length`。双方牌组、对方手牌及不可查看的墓地只给数量；对方额外和除外区域只列可公开身份的单卡。曾经观察到的事件仍留在历史。候选即使需要精确执行，也用不透明 ID，不向模型发送 UI 未显示的卡片 ID。卡片当前攻击力等动态字段只在当前区域收到相应 `QUERY_*` 时输出；未知不填默认值。位置 `instance_id` 只是位置键，不作为跨移动稳定 ID。

协议确实报告的事实可进入事件，例如玩家抽取数量、阶段变化、带来源位置的移动、收到的原因标志。程序不补写协议未说明的因果或“某效果已使用”等结论。对每一种游戏消息建立覆盖表：`parsed_fact`、`known_nonessential`、`unparsed_may_matter`。当前客户端已解析回合／阶段、抽卡、移动、终局、展示、连锁、LP、战斗、表示、盖放、对象、召唤及洗牌等消息；明确的更新包与决策提示归入 `known_nonessential`。剩余消息、格式截断或解析失败归入 `unparsed_may_matter`，保留安全的 `unparsed_game_message` 类型并将 `history_complete=false`；服务端拒绝自动决策。不发送原始二进制数据。覆盖判断须按对局轨迹和客户端表现验证，而非只按消息名猜测。

## 服务端事务与差异

服务端以 `(session_id, duel_id)` 隔离状态。接收同步请求时，校验数据库哈希、身份、事件连续性和重传内容，原子追加事件，再返回已持久化的连续 `ack_event_id`。决策请求还需校验 `prompt_id` 与严格递增的 `state_version`，在同一事务中追加事件、保存当前快照、生成净差异并记录请求指纹。重复的相同请求返回缓存结果；同版本内容不同或事件 ID 内容不同则冲突。持久化成功才允许模型作答。服务重启只能恢复通过校验的日志与检查点；不能用残缺文件冒充完整状态。

差异是前后两个完整可见快照的确定性比较：回合、阶段、LP、区域数量、明确可定位卡位及可信动态字段。它不解释原因。相同 ID 的多张卡、隐藏区进出和手牌重排应报告为区域变化或不确定变化，不能虚构某张卡的轨迹。若观测事件明确给出移动的前后位置，可在独立事件部分呈现；不能从净差异反推移动。每条变化带前后状态版本和字段路径；每个事件带原始事件序号与来源消息类型。

一期确定性测试端使用**每次请求的原子完整检查点**：事件、快照历史、请求指纹及差异装入同一份带校验和的本地文件，先在隔离副本应用变更，完整写入临时文件并 `fsync`，再原子替换；`ack_event_id` 只覆盖已经保存的连续事件前缀。文件名由会话与对局的组合哈希得到，避免把外来 ID 直接拼成路径。正式二期服务可在保持同样确认语义的前提下扩展为追加日志与周期检查点；此方案尚未实现。终局记录的归档和保留期限也需在二期服务实现中确定，默认不上传。模型的推测、计划和记忆存于独立命名空间，并标注证据和不确定性；它们不得写回权威镜像。

## 模型输入与查询工具

首次接管一局时给模型简洁的完整可见场面摘要，随后每个真实决策给：本次 `state_version`、有序新观测事件、快照净差异、当前提示和完整合法候选。事件与净差异始终是两种不同结构与中文描述。即使摘要做了裁剪，服务端也保留完整可分页的事件日志，并标明摘要覆盖的事件序号范围；不能静默丢弃关键事件。若决定动作所需的经过在截止时间内无法提供，交还人工。

只读工具从已确认镜像读取整体状态、指定玩家区域、指定位置的卡，以及按事件序号或状态版本分页的完整历史。Agent 每次决策默认接收新事件与净差异；是否调用工具回看此前事件、旧版快照或当前完整状态，由 Agent 自己决定。工具结果标明会话、对局、视角、版本及事件序号范围，使模型能够区分已确认事实、未收到的区间和自己的推测。每次查询绑定本方 `(session_id, duel_id, state_version)` 和鉴权身份；镜像落后于当前提示时拒绝给模型旧状态。工具和持久文件延续客户端可见性过滤，不能跨视角查询或绕过当前查看限制。第一版不实现 Agent 主动向客户端查询；完整快照已有的墓地、除外区、素材等资料由镜像查询。

## 人类只读视图

二期 Agent 服务还要把同一份已确认状态提供给人类查看。服务端提供只读查询层，按对局与视角返回最新场面、历史版本、事件时间线、净差异、决策提示和服务端答复；人类界面从查询层读取，不直接解析或修改检查点文件。现有决策响应只说明服务端发出了动作，不证明客户端已经执行；界面不得标成“已执行”，除非将来补入经客户端确认的执行回执。事件与差异分别展示，保留原始序号、来源和“未知／无法推断”的标记；不能把推测的卡片身份、移动原因或效果使用状态写成事实。模型的计划和推测若将来供人查看，须作为独立内容明确标注来源。

实时查看只能读取该人获授权的单一客户端视角，继续隐藏对方手牌、牌组和盖卡身份。开发者需要联合分析双方时，使用明确授权的离线录制分析流程，不把两个客户端视角合并进正在决策的 Agent 会话。视图应标明最新已确认的 `state_version`、`ack_event_id` 和更新时间；当前协议在真实决策时更新完整快照，`/v2/sync` 可在其间推进事件，因此界面不得把最近一次快照误称为逐帧实时场面。是否增加无决策时的快照推送，须按人类查看所需的刷新粒度单独决定。

## 故障与人工接管

客户端持有未确认事件直到服务端明确确认；达到缓存上限前分批同步。静默丢弃、请求体截断、序号跳跃和关键消息仅留下泛化类型都使历史不完整。`history_complete=false`、事件缺口、快照超限或状态冲突时服务端不运行模型，客户端保留人工提示。完整快照只修复当前状态，不修复事件历史。

网络结果不明时，重传原内容利用幂等接收；F10 从人工切回 Agent 时，客户端先调用 `/v2/status` 核对已确认的事件序号和状态版本，随后冻结新的快照。旧提示的动作一律失效；客户端只对当前待处理提示执行通过复核的动作。人工期间的观测继续保留，再次接管时先同步并明确记录控制权切换。人工期间出现不可恢复缺口则不让模型在假定历史完整的前提下接管。

## 交付与验证

1. 实现 v2 解析、状态模型和事务语义，并用构造夹具验证重复请求、事件乱序／缺口／冲突、版本倒退、原子写入及服务重启恢复。
2. 对 `ClientField` / `ClientCard` 逐字段补齐可见性和有效性判断，同时审计提示候选与事件；验证对手手牌、牌组顺序、盖卡、暂时不可查看区域及隐藏候选均不泄露身份。
3. 以已通过 GUI 验证的复杂场景和双客户端录制轨迹逐决策回放，比对镜像与当时客户端可见快照、事件顺序、差异、合法候选及动作；双侧轨迹只在离线测试中汇合。
4. 验证事件批量同步、人工接管／恢复、HTTP 超时和断线、服务重启、未知关键消息、队列上限及完整快照超限。二期还要验证模型历史工具与人类只读查询返回相同的已确认事实、历史分页无缺口、权限隔离及视图版本标记。分别报告单元、无头双客户端、GUI、macOS 和最终 Windows 的实际执行情况；未执行不写成通过。

二期的 LLM harness、规则书与卡片数据库技能、模型供应商接线，另行设计。三局两胜及换备牌、其他语言、观战等不属于本轮实现。
