# Agent 决斗客户端：第一期设计

> 状态：历史阶段设计。适用于一期客户端协议转换的取舍；继任的现行服务及状态数据流见[现行状态设计](agent-state.md)、[二期服务设计](agent-phase-2.md)和 [HTTP v3 契约](../contracts/agent-http-v3.md)。本文中技能资源“未纳入 Git”仅描述一期写作时的状态；现在两个运行时技能已纳入仓库。

## 背景与目标

客户端同时承担人类界面和 Agent 的可见状态、动作适配。第一期交付可在 macOS、Windows 上运行的联网单局 1v1 Agent 客户端、Python `agent_sdk`、确定性测试端和版本化契约。人工负责创建/加入房间及装载卡组；从赛前猜拳和先后攻选择到决斗终局由 Agent 接管。双方使用 `deck/test/test.ydk` 验收。

游戏服务端、`ocgcore`、`script` 和原有 CTOS/STOC 协议均不得修改。三局两胜及换备牌是后续任务；双打、观战、单机残局不在范围内。

## 架构

```text
STOC 二进制消息 → DuelClient 现有解析 → 可见状态/决策候选 → Agent 适配层
                                                        │
                                                  HTTP POST JSON
                                                        ↓
                                          确定性测试端 → agent_sdk
                                                        │
                                                语义动作 + 中文理由
                                                        ↓
客户端核对会话、提示、候选与参数 → 原有 SetResponseI/B + SendResponse → CTOS
```

Agent HTTP I/O 使用独立的 libevent `event_base`，不得阻塞游戏网络线程或渲染线程。网络回调仅复制数据并向客户端主线程投递命令；主线程在绘制锁外处理命令。一个客户端同时最多有一个待决策提示。人工接管立即使当前提示失效，迟到回复丢弃。自动模式异常时保留当前人工提示，不提交猜测动作。

客户端始终展示正常 GUI。语义动作直接使用既有响应编码，不合成键鼠事件，也不依赖弹窗渐隐的异步提交。必须防止 UI 自动连锁、自动区域等路径与 Agent 双重应答。

## 协议边界

- `docs/contracts/agent-http-v1.md` 定义客户端与 Agent 服务间的 JSON 结构、验证和 HTTP 错误语义。
- `docs/contracts/duel-actions.md` 列出赛前和决斗内每种请求的语义动作、原始响应映射及覆盖测试。
- 原始 CTOS/STOC 帧在本地诊断层以原始字节无损记录，未知消息亦保留。只向 Agent 发送客户端可见的语义状态；原始包和隐藏信息不得进入决策请求。
- 可见卡使用卡片 ID 表达静态身份，不传卡名或卡文。状态另提供当前区域、控制者、位置、表示形式、数值及提示内实例 ID；未知卡没有 ID。技能和规则书由第二期 Agent 服务自行查询。
- 快照对每次决策自包含，并附自上次决策以来的事件。事件仅表达客户端直接观测到的事实；不推断效果因果或隐藏身份。
- 选择类响应必须保留服务端候选原始顺序。动作 ID 只在当前提示有效，不能把卡片密码当作实例或动作 ID。

## 组件与交付顺序

1. 先实现二进制帧审计与语义模型，写契约夹具验证收发不改变原有协议。
2. 实现全部 20 类决斗决策及赛前两类选择的候选生成、响应编码和客户端验证。`SUM`、`TRIBUTE`、`UNSELECT_CARD` 等组合约束需要专用校验。
3. 实现独立 `agent_sdk`（Python 3.12，仅标准库）：契约模型、候选/参数验证、结构化意图到语义动作转换。不含模型、技能、HTTP 服务。
4. 实现确定性 HTTP 测试端，调用 `agent_sdk`，以固定策略完成正常对局。
5. 接入 GUI 人工/Agent 切换、超时接管、私有诊断日志和配置。

## 客户端运行配置

一期通过环境变量启用：`YGOPRO_AGENT_ENABLE=1`。默认连接 `127.0.0.1:8910`；可用 `YGOPRO_AGENT_HOST`、`YGOPRO_AGENT_PORT` 更改地址。客户端启动时从工作目录的 `cards.cdb` 计算 SHA-256；若卡库位于其他位置，设置 `YGOPRO_AGENT_DB_PATH`。局域网连接需设置 `YGOPRO_AGENT_TOKEN`，与测试端令牌一致。`YGOPRO_AGENT_TIMEOUT_MS` 控制单次 HTTP 超时，默认 15000 毫秒；`YGOPRO_AGENT_LOG_PATH` 可指定本地 JSONL 诊断轨迹。F10 在 Agent 和人工之间切换，错误时自动交还人工并在聊天区域显示原因。

在仓库根目录启动测试端：`uv run --project agent_sdk python -m agent_sdk.test_server --cards-db cards.cdb`。两个客户端分别配置相同的 Agent 地址和卡库；房间准备、选用 `deck/test/test.ydk` 仍由人工完成。无计时单局适合先完成协议覆盖验收。

自动化回归还提供测试模式：两个独立客户端进程通过环境变量指定 host/guest、端口和卡组路径，由客户端直接调用既有 LAN 连接、卡组提交、准备和开局 API。决斗动作仍由同一 AgentController 执行并经真实 CTOS/STOC 往返；测试模式使用 Irrlicht Null driver，不依赖点击或桌面自动化。它仅用于本机单局回归，不改变正式用户的建房流程，也不修改游戏服务端。

## 资源与部署

复用已有 `libevent::extra`、`nlohmann-json`，第一期不增加客户端第三方依赖。测试端默认绑定本机回环地址；局域网监听必须显式启用并配置令牌。局域网 HTTP 不加密，只用于可信网络。**历史约定**曾由用户手动维护 `.agents/skills`，不纳入仓库；现行实现已把两个运行时技能纳入 Git，仍与客户端共用本地 `cards.cdb`。第一期单元测试使用小型夹具。数据库哈希不匹配时禁用自动决策。

## 失效与一致性

请求含 `session_id`、`duel_id`、`prompt_id`。每次决策只执行一个动作；提交后等待新的游戏消息。客户端收到过期、重复、未知或非法动作时返回结构化错误并交还人工。超时/断线亦交还人工。Agent 的中文理由只在本方 GUI 和本地日志显示，不参与执行。`MSG_RETRY` 必须取消旧提示并重新发起决策。客户端的任何自动应答路径都要明确纳入提交审计，且不得与待处理 Agent 响应竞争。

## 验收

- macOS 和 Windows 均构建并完成双客户端局域网单局对战。
- 两客户端载入 `deck/test/test.ydk`，人工完成房间准备后，连续三场不同随机起手对局，从赛前选择至终局无人工救场、非法响应、重复提交或未覆盖提示。
- 协议轨迹夹具覆盖所有支持的决策类型，并验证响应字节与现有 UI 编码一致、原始帧可无损还原、未知包保留。
- 验证人工接管、超时、断线、过期回复、非法动作、数据库不一致、隐藏信息过滤；计时房间单独验证超时接管，自动对局使用无计时房间。
- 未能在目标平台执行的验收项必须单独标记为未完成，不等同于构建通过。

## 风险

`ClientAnalyze` 同时处理 UI、动画和信号等待，不能把 Agent HTTP 回调直接插入其中阻塞。弹窗渐隐可能延迟 `SendResponse`，需要统一提交上下文防止重复。构建只使用仓库 `CMAKE_BUILD.md` 所述的 CMake/vcpkg 流程。**历史状态**：一期写作时卡片数据库及两个技能未纳入 Git；现已纳入两个技能，根目录 `cards.cdb` 仍由本地维护。确定性测试端若仅按第一个候选选择，复杂卡组可能循环，策略需保证推进或明确报告无法推进。
