# 决斗场景制作与审核

> 状态：现行流程设计。场景字段和失败语义以[场景 v1 契约](../contracts/agent-scenario-v1.md)、[随机场景 v2 契约](../contracts/agent-scenario-v2.md)为准；操作入口见[场景制作指南](../guides/duel-scenario-authoring.md)。

## 背景和目标

人工设计并操作的双客户端对局能覆盖真实的客户端消息、可见状态与动作链路。录制器负责保留双端证据并生成动作草稿；开发 Agent 根据用户自然语言目标、规则资料和录制证据编写断言与说明；程序执行断言；人类审核目标解释和证据充分性后决定是否入库。

场景回放验证协议及执行链路，不评价 LLM 的战术决策。原始双端录制包含各自的隐藏信息，只保存在 Git 忽略的 `out/duel-recordings/`，不得合并成任何单方 Agent 的观测。

## 工作流

1. 用户提供测试目标。开发 Agent 保留原话，整理双方视角和待确认处；具体 `goal.md` 结构由场景契约规定。
2. 以显式场景类型启动双客户端录制。确定性与随机场景分开处理；类型、牌序约束及可记录的随机事件以对应场景契约为准。
3. 编译器核对录制完整性、牌组、双端提示与响应，输出带来源的候选。开发 Agent 将目标映射到各端可见事件及后置状态断言；无法观察的目标明确记为未验证。
4. 场景执行器运行候选并给出逐断言证据；随机场景另报告结果覆盖。失败与覆盖不足的判定以场景契约为准。
5. 开发 Agent 写明自然语言目标与实际证据的对应关系。用户审核后，才把通过审阅的场景收入 `tests/scenarios/`；目录材料和索引要求以场景契约为准。

该工作流由开发用 `.agents/skills/duel-scenario-authoring/` 引导，调用确定性工具；技能不进入运行时决斗 Agent 或发布包。协议和场景格式以 `docs/contracts/` 为准，技能不复制字段契约。

## 随机场景的设计取舍

随机结果会让整局动作序列分叉，不能把一次录制的具体结果当成以后每次必然发生。当前选择只检查效果完成后的可见事实及结果覆盖，按结果选择不同后续动作的完整分支留待后续。单方断言始终只使用该方可见信息；格式、采样与失败语义以[随机场景 v2 契约](../contracts/agent-scenario-v2.md)为准。

设计上区分单次断言成立与多次尝试中观察到目标结果，避免用采样成功掩盖单次协议失败，也不宣称有限采样穷尽全部结果。

## 验证策略与风险

- 严格场景保留既有 v1 读取与运行语义。场景格式变更需有版本、兼容测试和错误诊断。
- 随机选卡消息必须按单方可见性转为语义事件；隐藏位置和卡片身份不得从另一端录制补齐。
- 场景目录 README 的规则依据与实际观测证据分开。YAML 成功回放仅证明其断言通过，不自动证明自然语言目标。
- macOS 先验证协议测试、场景工具测试和双客户端回放。实际随机效果场景需有相应录制才能宣称真实对局覆盖；Windows 最后验证。
