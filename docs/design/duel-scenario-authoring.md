# 决斗场景制作与审核

## 背景和目标

人工设计并操作的双客户端对局能覆盖真实的客户端消息、可见状态与动作链路。录制器负责保留双端证据并生成动作草稿；开发 Agent 根据用户自然语言目标、规则资料和录制证据编写断言与说明；程序执行断言；人类审核目标解释和证据充分性后决定是否入库。

场景回放验证协议及执行链路，不评价 LLM 的战术决策。原始双端录制包含各自的隐藏信息，只保存在 Git 忽略的 `out/duel-recordings/`，不得合并成任何单方 Agent 的观测。

## 工作流

1. 用户提供测试目标。`goal.md` 保留原话，并另列开发 Agent 整理的目标、双方视角及待确认处。既有录制后补目标时标明“事后提供”。
2. 以显式场景类型启动双客户端录制。两类都使用“不洗牌”固定牌序；`deterministic` 是默认值，`random` 允许该场景声明的目标随机操作。录制类型不可由偶然观察到的结果推断或静默转换。
3. 编译器核对录制完整性、牌组、双端提示与响应，输出带来源的候选。开发 Agent 将目标映射到各端可见事件及后置状态断言；无法观察的目标明确记为未验证。
4. 场景执行器运行候选并给出逐断言证据。随机场景还报告每次结果、目标结果覆盖情况和尝试次数。任何一次协议、动作或断言失败都立即失败；达到采样上限仍缺目标结果时报告覆盖不足。
5. 开发 Agent 编写 README，逐项目标标为“已验证”“部分验证”或“未验证”，附机器报告及限制。用户审核后，才把 `scenario.yaml`、`host.ydk`、`guest.ydk`、`goal.md`、`README.md` 放入 `tests/scenarios/<功能名>/` 并更新总索引。

该工作流由开发用 `.agents/skills/duel-scenario-authoring/` 引导，调用确定性工具；技能不进入运行时决斗 Agent 或发布包。协议和场景格式以 `docs/contracts/` 为准，技能不复制字段契约。

## 随机场景第一版边界

每个场景只聚焦一次目标随机操作；一次操作可产生多个结果值。前置动作仍可严格指定。随机结果出现后，只支持不依赖结果而改变动作序列的流程，至目标效果完成后的 checkpoint。断言可以依据实际结果检查各方可见事件和后置状态，但绝不从双端日志拼出单方不可见卡身份。需要按结果选择不同动作的完整分支保留原始录制并报告暂不支持。

“一次运行通过”表示该次结果对应的断言成立；“目标结果覆盖”表示在有限次数内观察到了目标中列出的结果。两者分开记录，重复运行不掩盖任何一次失败，也不保证一定观察到所有可能值。

## 验证策略与风险

- 严格场景保留既有 v1 读取与运行语义。场景格式变更需有版本、兼容测试和错误诊断。
- 随机选卡消息必须按单方可见性转为语义事件；隐藏位置和卡片身份不得从另一端录制补齐。
- 场景目录 README 的规则依据与实际观测证据分开。YAML 成功回放仅证明其断言通过，不自动证明自然语言目标。
- macOS 先验证协议测试、场景工具测试和双客户端回放。实际随机效果场景需有相应录制才能宣称真实对局覆盖；Windows 最后验证。
